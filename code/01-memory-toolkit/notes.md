## Debug 堆 vs Release 堆（D20）
1. 在Debug堆中，内存块被free释放之后，**不会立刻复用这块内存**，还会把释放出来内存全部填充上`0xDD`标记。如果程序不小心读写已经释放掉的内存，就会碰到这个特殊标记，很容易就暴露“使用已释放内存”这个bug。
2. Debug堆给每一块用户内存的左右两侧，额外设置了警戒线（no‑man's land，无人区）。一旦代码发生越界读写，就会破坏警戒线，调用free的时候就触发报警，检测缓冲区越界问题。
3. 二者设计目标不一样：**Debug堆的首要目标是抓bug（抓虫），牺牲一部分运行效率；Release堆优先追求运行速度，做性能优化。两套堆拥有完全不一样的行为特性。

>（加分项，自己实验的联系）我做实验的时候，D19那5块内存释放完，再new出来得到的是全新地址，旧内存不会拿来重复分配，根源就是Debug堆不会马上复用释放后的内存块。
## cookie 何时存在（D21）

编译器需要挨个调用析构的时候，才安排 cookie；不需要挨个析构，就不要 cookie。不是堆运行时去查数量，很多信息编译期就定好了。

## 为什么「模块基址+偏移」抗重启、抗更新（W6）

1) **纯偏移失效的根因**：如果偏移是相对堆/栈这类动态区域的基址，那些基址每次运行都随机
   —— 实测证据：hp 地址 A1=0x39dd6ff980，重启后 A2=0xe797f5fcd0，完全不同。
   所以纯偏移**每次启动就失效**，这和"程序更新"无关。
2) **「模块基址+偏移」抗重启**：模块基址每次可以从目标进程重新获取
   —— 实测：10/10 模块基址 0x7ff635a70000，10/14 为 0x7ff7fd9b0000（跨会话 ASLR）。
   而模块内偏移由**编译器+链接器在构建期固定**，同一二进制每次运行都不变。
   所以：基址实时取 + 偏移写死 = 抗重启。
3) **抗更新是另一层**：从全局对象出发的链，小版本更新后通常只需微调少量内层偏移；
   而硬编码绝对地址/深链偏移在更新后必须重新扫描。

## 第 1 小节：两条路线的源头（3–4 句）

scan10 远端 PEB 手解，读取目标进程用户态 PEB→Ldr→InMemoryOrderModuleList 双向链表。
PSAPI 的 EnumProcessModulesEx 并非读取内核缓存，它内部同样是远程读取这份 PEB-Ldr 链表数据。
两条路径只是读取方式不同，读取的是同一份用户态台账。
结论：一处台账、两个读者。

## 第 2 小节：为什么 “列表一致” 证明不了真相（4–5 句）

手工映射注入的模块不经过系统加载器，不会被写入 PEB-Ldr 链表，两条路线都无法发现这类隐藏模块。
只要篡改这一处用户态链表，就能同时骗过 PEB 手解与 PSAPI 接口，两次读数不会产生任何独立新信息。
D42 曾经把 scan9 与 scan10 称作两条完全独立的检测路径，这个结论存在错误。
二者返回结果只能代表链表解析逻辑实现正确，完全不能保证枚举出来的模块列表就是进程真实加载状态。

## 第 3 小节：三个名字，各管一摊

1. EPROCESS：进程对应的内核对象本体，它本身并不存储进程模块链表。
2. VAD（虚拟地址描述符树）：内核维护的进程地址空间映射记录，用户态摘除 Ldr 链表节点无法篡改这份内核数据。
3. PsLoadedModuleList：全局内核驱动模块清单，只记录驱动，不记录进程内加载的用户态 DLL。

## 第 4 小节：交叉验证数据源 + 检测细节

### 三项独立数据源

1. VAD 树枚举：需要内核驱动或调试器读取内核 VAD 树，不受用户态 Ldr 链表篡改影响。
2. 全地址空间页扫描：调用 VirtualQueryEx 遍历整个进程地址空间，识别 PE 镜像内存块。
3. ETW 内核加载遥测：依托系统内核加载事件日志，捕获所有真正完成映射的镜像。

### 两条检测细节

合法 LoadLibrary 加载的 DLL 内存页属性为 MEM_IMAGE；手工映射注入的内存页属性为 MEM_PRIVATE。
该内存属性差异，本身就是识别手动映射注入的核心检测依据。
