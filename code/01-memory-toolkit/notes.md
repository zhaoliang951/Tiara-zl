## Debug 堆 vs Release 堆（D20）
1. 在Debug堆中，内存块被free释放之后，**不会立刻复用这块内存**，还会把释放出来内存全部填充上`0xDD`标记。如果程序不小心读写已经释放掉的内存，就会碰到这个特殊标记，很容易就暴露“使用已释放内存”这个bug。
2. Debug堆给每一块用户内存的左右两侧，额外设置了警戒线（no‑man's land，无人区）。一旦代码发生越界读写，就会破坏警戒线，调用free的时候就触发报警，检测缓冲区越界问题。
3. 二者设计目标不一样：**Debug堆的首要目标是抓bug（抓虫），牺牲一部分运行效率；Release堆优先追求运行速度，做性能优化。两套堆拥有完全不一样的行为特性。

>（加分项，自己实验的联系）我做实验的时候，D19那5块内存释放完，再new出来得到的是全新地址，旧内存不会拿来重复分配，根源就是Debug堆不会马上复用释放后的内存块。
## cookie 何时存在（D21）

编译器需要挨个调用析构的时候，才安排 cookie；不需要挨个析构，就不要 cookie。不是堆运行时去查数量，很多信息编译期就定好了。

## 为什么「模块基址+偏移」抗重启、抗更新（W6）

1) **纯偏移失效的根因**：如果偏移是相对堆/栈这类动态区域的基址，那些基址每次运行都随机
   —— 实测证据：hp 地址 A1=0x39dd6ff980，重启后 A2=0xe797f5fcd0，完全不同。
   所以纯偏移**每次启动就失效**，这和"程序更新"无关。
2) **「模块基址+偏移」抗重启**：模块基址每次可以从目标进程重新获取
   —— 实测：10/10 模块基址 0x7ff635a70000，10/14 为 0x7ff7fd9b0000（跨会话 ASLR）。
   而模块内偏移由**编译器+链接器在构建期固定**，同一二进制每次运行都不变。
   所以：基址实时取 + 偏移写死 = 抗重启。
3) **抗更新是另一层**：从全局对象出发的链，小版本更新后通常只需微调少量内层偏移；
   而硬编码绝对地址/深链偏移在更新后必须重新扫描。

| 权限位 | 管什么 | 何时必须加 | 报错指纹（缺它时） |
|------|------|----------|----------------|
| PROCESS_VM_READ | 读目标内存(ReadProcessMemory) | 需要读时必须加 | RPM 失败，err = 5（拒绝访问） |
